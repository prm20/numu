What We Set Up and Fixed
1. Making the import_discs Management Command Work

Initial issue:

You tried to run:
python manage.py import_discs --disc 1 --dry-run --json-dir json


Django said:

> Unknown command: 'import_discs'

Cause:

import_discs.py was at the project root:
• backend/import_discs.py

But Django expects custom management commands inside an app, under:
• <app_name>/management/commands/

Fix: moved the command and created packages

From backend:
mkdir -p numu/management/commands
touch numu/management/__init__.py
touch numu/management/commands/__init__.py
mv import_discs.py numu/management/commands/


Resulting structure:
• backend/numu/management/__init__.py
• backend/numu/management/commands/__init__.py
• backend/numu/management/commands/import_discs.py

After this, Django recognized the import_discs command.
---
2. Fixing the JSON_DIR NameError

Next error when running the command:
NameError: name 'JSON_DIR' is not defined. Did you mean: 'self.JSON_DIR'?


Cause:

Inside Command.add_arguments, the help text used JSON_DIR without self. even though JSON_DIR is a class attribute.

Original snippet:
parser.add_argument(
    '--json-dir', type=str,
    help=f'Directory containing disc JSON files. Default: {JSON_DIR}'
)


Fix:

Edited backend/numu/management/commands/import_discs.py:
parser.add_argument(
    '--json-dir', type=str,
    help=f'Directory containing disc JSON files. Default: {self.JSON_DIR}'
)


That resolved the NameError.

5. Admin Customization for Lessons

Initially, numu/admin.py auto-registered all models:
from django.contrib import admin
from django.apps import apps

# Get the app config for the "numu" app
app_config = apps.get_app_config("numu")

# Automatically register all models in this app with the admin site
for model in app_config.get_models():
    try:
        admin.site.register(model)
    except admin.sites.AlreadyRegistered:
        # In case something was registered manually elsewhere
        pass


This worked, but we had no:
• Filter by disc for Lessons.
• Control over which fields were shown/clickable.

We added a custom admin for Lesson, keeping the auto-registration loop for everything else.

Final structure (conceptually):
from django.contrib import admin
from django.apps import apps
from .models import Lesson  # plus others like Entry later if desired

# Custom admin for Lesson so we can control list + filters + clickable column
@admin.register(Lesson)
class LessonAdmin(admin.ModelAdmin):
    list_display = ("lesson_number", "title", "disc")
    list_filter = ("disc",)
    list_display_links = ("title",)  # Title is the clickable link

# Auto-register all other models
app_config = apps.get_app_config("numu")

for model in app_config.get_models():
    try:
        admin.site.register(model)
    except admin.sites.AlreadyRegistered:
        pass


Effect in the admin (Lessons page):
• You can now see columns: lesson_number, title, disc.
• Only title is clickable (as you requested).
• There’s a filter on the right side: filter lessons by disc.

6. Disc Titles, IDs, and JSON Meta

Current situation:
• All 4 discs initially used the same title from JSON:
  • "Numu Yadooape (Northern Paiute Language)".
• In the admin, this made the disc filter look like the same label repeatedly.
• The JSON meta for each disc looks like:"meta": {
  "title": "Numu Yadooape (Northern Paiute Language)",
  "dialect": "Pyramid Lake Paiute Tribe",
  "writing_system": "Wycliffe",
  "disc": 1,
  "total_pages": 14
}


Key points we clarified:
• The importer and DB relationships rely on id, not title:
  • Disc.id = 1,2,3,4 is the backbone.
  • Lessons have lesson.disc (FK to Disc).
  • Entries (and other content) have entry.lesson (FK to Lesson), so entry.lesson.disc ties them back.
• Changing Disc.title in the admin is safe:
  • Does not affect imports.
  • Does not break existing data.
  • Does not hurt future React/React Native or AI usage, as long as those use id (or another stable field) rather than checking title literals.

You can, for example, rename them in the admin to:
• Disc 1 – Numu Yadooape (Northern Paiute Language)
• Disc 2 – Numu Yadooape (Northern Paiute Language)
• Disc 3 – Numu Yadooape (Northern Paiute Language)
• Disc 4 – Numu Yadooape (Northern Paiute Language)

or any other human-friendly naming.

About JSON titles:
• You do not need to change the JSON meta.title to match whatever you rename in the admin.
• JSON is only used as the source for import; the DB is now the source of truth.
• Only reason to change JSON titles would be for your own long-term cleanliness if you ever blow away the DB and want to re-import from scratch with consistent human-facing titles.

          • Specialized models (numbers, animals, verb paradigms, colors, prayers, suffix examples, sentence entries, etc.).
          • ReviewFlag rows where appropriate.
      • When --dry-run is used:
        • Does all parsing, validation, and counting.
        • Prints a summary, but does not write anything to the DB.
      • When run without --dry-run:
        • Commits all changes to the database and prints detailed summaries per disc.

PostgreSQL Setup & Configuration

This project uses PostgreSQL as the primary database for the Django backend.
1. Local Postgres database

On the local dev machine, you should have a PostgreSQL server running and a database created for this project. A typical setup looks like:
• Postgres running on: localhost
• Port: 5432 (default)
• Database name: numu_db
• Username: pmatson
• Password: your_password_here

Example SQL to create the DB and user (run in psql as a superuser like postgres):
CREATE DATABASE numu_db;
CREATE USER numu WITH PASSWORD 'your_password_here';
GRANT ALL PRIVILEGES ON DATABASE numu TO numu;


Adjust names/passwords as needed.
2. Django DATABASES setting (config/settings.py)

In config/settings.py, the DATABASES setting is configured to use PostgreSQL. It should look roughly like this (edit to match your real credentials):
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': os.getenv('DATABASE_NAME', 'numu_db'),
        'USER': os.getenv('DATABASE_USER', 'pmatson'),
        'PASSWORD': os.getenv('DATABASE_PASSWORD', ''),
        'HOST': os.getenv('DATABASE_HOST', 'localhost'),
        'PORT': os.getenv('DATABASE_PORT', '5432'),
    }
}


If your DB name/user/password differ, update them here.
3. Applying migrations

Once PostgreSQL is running and the DATABASES setting is correct, the schema is created by running migrations from the backend project root:
cd /Users/pdogg/Documents/numu/dev/backend
source .venv/bin/activate
python manage.py migrate


This:
• Creates the core Django tables (auth, admin, sessions, etc.).
• Creates all tables for the numu app (Disc, Lesson, Entry, Lexeme, and all related models).
4. Creating a superuser

To use the Django admin with this Postgres-backed DB, a superuser account is created via:
python manage.py createsuperuser


You choose:
• username
• email (optional)
• password

This user logs into /admin/ and has full access to view/edit all numu models.
5. Verifying the Postgres connection

To confirm Django is talking to Postgres correctly:
1. Run the dev server:python manage.py runserver

2. Visit:
  • http://127.0.0.1:8000/admin/
3. Log in with the superuser you created.
4. You should see:
  • “NUMU” section with models like Discs, Lessons, Entries, Lexemes, etc.
  • The imported data (after running the import commands) available there.

If there’s a connection error (e.g., “could not connect to server: Connection refused” or “FATAL: password authentication failed”), it usually means:
• Postgres isn’t running, or
• DB name/user/password/host in DATABASES don’t match the actual Postgres config.
